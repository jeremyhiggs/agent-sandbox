# Agent container

Run a shell, Codex, OpenCode, or Claude Code in a disposable Linux VM using
Apple's `container` runtime. All images include Wolfi Linux, mise, Node, pnpm,
Git, Git LFS, GitHub CLI (`gh`), Jujutsu, agent-browser, Chrome for Testing, and Herdr's `hc`.
The agent images add one agent CLI each. Scripts are TypeScript executed by Node.

## Setup

Use an Apple silicon Mac supported by Apple's container runtime. Install mise,
then run these commands in this repository:

```sh
mise trust
mise install
mise run setup
container system start
mise run build
mise run check
mise run check:image
mise run scan
mise run install
```

`mise.toml` declares the host tools, including Apple's macOS-only runtime, and
pins image tool versions. Builds use exact OS package locks, base image digests,
archive checksums, and frozen pnpm graphs. See [reproducibility](docs/reproducibility.md).

Installation creates `~/.local/bin/agent-container`. Keep that directory on
`PATH` and keep this repository at its installed location: the command loads its
pinned mise environment, then restores your original working directory.
`--bin-dir PATH` selects another installation directory. Installation refuses to
replace an unrelated command and removes the previous `codex-container` shim
only if its contents match the shim generated by this repository.

The repository directory can remain named `codex-container`. From another
folder, use `mise -C /path/to/codex-container run install`.

## Launch a workload

Run these commands from any existing Git checkout, linked worktree, or JJ workspace:

```sh
agent-container
agent-container --agent codex
agent-container --agent codex --prompt 'Run the tests and fix failures'
agent-container --agent opencode --prompt 'Review this checkout'
agent-container --agent claude
agent-container --exec pnpm test
agent-container --agent codex --exec codex exec 'Review the changes'
agent-container --agent codex --exec bash
agent-container --exec sh -lc 'mise trust && mise install && mise run test'
```

A bare invocation opens Bash in the base image. `--agent` selects the image,
persistent state, and default command. `--prompt` requires `--agent` and supplies
an initial **interactive** prompt. It cannot be combined with `--exec`.
For native headless modes or login commands, use `--agent` with `--exec`.

`--exec` consumes all remaining arguments as literal program arguments. Put
launcher options before it. Shell syntax requires an explicit shell such as
`sh -lc`. There is no `exec` subcommand.

The default guest has four CPUs and 4 GB of memory. Options include:

```sh
agent-container --checkout /path/to/worktree --cpus 6 --memory 8G --agent codex
agent-container --dns 8.8.8.8 --exec bash
```

`--image TAG` overrides the selected image; it must contain the chosen program.
`--home PATH` selects the host state/skills source without mounting that entire
home. Apple builds and guests default to DNS resolver `1.1.1.1`;
`CONTAINER_DNS` overrides that default. Host DNS settings are unchanged.

Exit the workload to destroy the VM. With Herdr, detaching also destroys the VM.
Mounted checkout changes and agent state remain on the host. The launcher's
exit status follows the workload. A forced launcher kill or Mac shutdown can
leave a guest behind; use `status` and `stop` to remove it.

## Images

| Image                      | Default workload | Agent CLI added |
| -------------------------- | ---------------- | --------------- |
| `agent-container:base`     | Bash             | None            |
| `agent-container:codex`    | Codex            | Codex           |
| `agent-container:opencode` | OpenCode         | OpenCode        |
| `agent-container:claude`   | Claude Code      | Claude Code     |

Chrome and agent-browser are in the common base, so Codex with browser access
uses the ordinary Codex image. There are no browser/agent combinations to build.
`mise run build` builds all four Dockerfile targets sequentially and reuses the
common base layers. To build just one, use
`agent-container build --profile codex`. The Dockerfile's idle command lets the
launcher manage VM lifetime; the launcher chooses the foreground workload.

Images contain no npm, npx, compilers, make, or development headers. Install
repo-specific dependencies inside the guest with mise or APK. These guest disk
changes disappear on teardown. No host browser or browser profile is mounted.

## Optional Herdr integration

```sh
agent-container --herdr --agent codex
agent-container --herdr
```

Without `--herdr`, execution uses `container exec` directly and does not require
host `hc`. Herdr workload launches require interactive stdin and stdout. For
piped input or redirected output, omit `--herdr`; the launcher rejects that
combination before creating a VM rather than dropping input. Retained `start --herdr` registration also works from scripts.
With `--herdr`, install host `hc` matching `IMAGE_HC_VERSION` in `mise.toml`. The launcher registers a guest machine, starts a terminal in the
guest's independent core, and labels it with new Herdr space/tab IDs. Herdr can
adopt that terminal as a new session while preserving the selected session.
The app need not be open when the terminal starts.

The transport is `hc machine add --via 'container exec -i … sh -c'`. No SSH
server, host socket mount, or forwarded host core configuration is required.
Guest processes do not inherit the host core's machine connections. Normal
registration is used because Herdr hides `--temp` machines. Teardown removes
both the registration and VM. This grants host supervision of the guest; it
keeps the host core outside the agent's mounted filesystem.

## Keep a guest running

```sh
agent-container start --name ac-feature --agent codex --herdr
agent-container shell ac-feature
agent-container status
agent-container stop ac-feature
```

`start` retains an idle VM. With `--herdr` it also registers the guest, but does
not start an agent or create a workload session. Use host `hc run --on ac-feature`
to launch managed terminals, or use the guest shell. `attach ac-feature` attaches
to a terminal named `agent` if you created one through hc. The launcher deletes
only guests with its ownership label and `ac-` name prefix. Existing `cs-` guests
with the previous ownership label remain visible and can be stopped after upgrading.

## Shared files and authentication

| Host content                                            | Access                   | When            |
| ------------------------------------------------------- | ------------------------ | --------------- |
| Selected checkout and linked Git/JJ metadata            | Read/write, same paths   | Every launch    |
| `~/.agents/skills` and direct symlink targets           | Read-only, same paths    | When present    |
| Normal `~/.codex`, selected skill/plugin/config targets | Read/write, same paths   | `--agent codex` |
| `~/.local/share/agent-container/AGENT/home`             | Read/write as guest HOME | Claude/OpenCode |

Mounts are printed before startup. The selected checkout and shared Git/JJ refs
can be modified or deleted by the agent. Sibling checkout contents are not
mounted. Host SSH/AWS directories, credential helpers, signing agents, global
Git configuration, runtime control sockets, and host hc state are not mounted.
Configure a guest Git identity if it needs to commit. `gh` is installed without
mounting host GitHub credentials; authenticate inside the guest if needed. Image builds never include
checkout contents, user configuration, or credentials.

Codex uses your normal `.codex` directory and starts with
`--no-daemon --dangerously-bypass-approvals-and-sandbox` and
`cli_auth_credentials_store="file"`. An existing `auth.json` and its updates
persist. Keychain-only login does not follow a directory mount. To log in using
file storage:

```sh
agent-container --agent codex --exec codex -c 'cli_auth_credentials_store="file"' login --device-auth
```

Claude and OpenCode use dedicated persistent Linux homes. Their login/config
files survive VM teardown; their macOS login state is not imported. Start the
agent and follow its login flow, or run its native auth command with `--exec`.
These directories are separate from your host agent installations. A base shell
mounts no agent credentials. Claude retains its normal permission prompts.

Normal Codex configuration and skills can reference macOS tools, MCP servers, or
host-only paths. Those require Linux equivalents. Concurrent Codex host/guest
processes share a writable login cache; avoid simultaneous login/logout actions.
Skills inside `.codex` are writable unless a read-only shared skills mount covers
them. Shared skills are available as files; discovery rules vary by agent.

`.codex` itself must be a real directory. Skill links must point directly to
canonical targets; chained links are rejected. Linked `auth.json` and
`config.toml` must stay inside the checkout or Codex directory so atomic file
replacement persists. Mounts that expose the whole host home are rejected.

## Repository mise configuration

The mounted checkout contains its mise configuration. Review it, then run
`mise trust`, `mise install`, and its tasks inside the guest. System dependencies
can be declared with `[bootstrap.packages]` and applied with
`mise bootstrap packages apply --manager apk`. See the tested examples and
compatibility limits in [the Wolfi choice](docs/base-image.md).

The image does not automatically trust repo configs or run their hooks. Mise
selects language tools; Wolfi APK supplies native libraries, compilers, and
headers as needed. Wolfi uses glibc, but Debian package names, `apt` commands,
and every prebuilt binary are not universally compatible. Do not mix Alpine
and Wolfi packages. Guest tool caches disappear except for files within the
explicitly mounted persistent state.

## Checks and CI

```sh
mise tasks
mise run fmt
mise run check
mise run audit
mise run build
mise run check:image
mise run scan
mise run smoke:cli
```

`check` runs format/lint checks, TypeScript, unit tests, and lock validation.
`check:image` tests all four image inventories, agent separation, and an actual
agent-browser page load. `smoke:cli` uses fake state and a disposable linked
worktree to test shell/custom commands, literal arguments, exit status, state
persistence, mount boundaries, optional hc integration, and teardown. Its hc
server uses scratch configuration/state and a separate session. It makes no
model request and does not change the selected session in your normal core.

CI builds all profiles on amd64 and arm64, checks each, and runs Trivy image
scans. `build:ci`, `check:image:ci`, and `scan:ci` use Docker on Linux. Repository
Trivy, pnpm audits of all dependency graphs, and Chrome freshness are separate
audits. CI runs daily at **00:00 UTC**, plus push, pull request, and manual
triggers. A remote is required to activate the configured workflow; this repo
currently has none. There are no dependency update PR bots.

HIGH/CRITICAL findings fail the security gates, including unfixed findings.
Complete Trivy reports remain under `.artifacts/` and in CI artifacts. Scanner
coverage of downloaded native binaries and Chrome is limited; version/checksum
and browser freshness checks complement the scans. See [verification](docs/verification.md)
for tested behavior and limits.
