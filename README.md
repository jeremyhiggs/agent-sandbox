# Agent sandbox

Version **0.1.0**. See the [release notes](CHANGELOG.md) for scope and limitations.

Run shells, Codex, OpenCode, or Claude Code in a named Linux sandbox using
Apple's `container` runtime. All images include Wolfi Linux, mise, Node, pnpm,
Git, Git LFS, GitHub CLI (`gh`), agent-browser, Chrome for Testing, and Herdr's `hc`.
The agent images add one agent CLI each. Scripts are TypeScript executed by Node.

## Setup

Use an Apple silicon Mac supported by Apple's container runtime. Install mise,
then clone the repository into a directory named `agent-sandbox`:

```sh
git clone https://github.com/jeremyhiggs/agent-sandbox.git agent-sandbox
cd agent-sandbox
```

Run these commands in the repository:

```sh
mise trust
mise install
mise run setup
container system start
mise run build
mise run check
mise run check:image
mise run scan
mise run install
```

`mise.toml` declares the host tools, including Apple's macOS-only runtime, and
pins image tool versions. Builds use apko's native OS recipe and lockfile, a pinned
mise image digest, archive checksums, and frozen pnpm graphs. The Dockerfile
builds on the OS filesystem assembled by apko. See [reproducibility](docs/reproducibility.md).

Installation copies the runtime scripts, image recipes and locks, and bundled
guidance to `~/.local/share/agent-sandbox`, then creates a small launcher at
`~/.local/bin/agent-sandbox`. Keep the bin directory on `PATH`. The checkout can
move or be removed after installation. Re-run `mise run install` to update the
installed copy after changing this repository.

The command loads its copied mise pins, then restores your original working
directory. External tools such as Node and Apple's container CLI remain managed
by mise; their executables are not copied into the installation. Installation
trusts the copied `mise.toml`. `--bin-dir PATH` and `--install-dir PATH` override
the command and runtime locations. The runtime directory is installer-owned;
do not keep project files there. Installation refuses to replace an unrelated
command or directory and removes previous `agent-container` or
`codex-container` shims only if their contents match a launcher generated by this
repository.

Agents can read the full guidance with `agent-sandbox --skill`; `--help`
advertises it. It includes recommended launch, sharing, supervision, and cleanup
workflows. The guidance ships with the CLI and needs no separate skill installation.

Use `agent-sandbox --version` to check the installed version. Image tool versions
are pinned independently in `mise.toml` and the committed image locks.

From another folder, use `mise -C /path/to/agent-sandbox run install`.

## Create and use a sandbox

Run commands from any directory. No checkout is shared by default; the guest
starts in its own persistent `/workspace`. Use `--mount-git` to share the current
checkout or linked worktree, or `--mount-git PATH` to select one elsewhere.
The shell or agent starts at the selected checkout's root, at the same absolute
path as on the host. A path inside a checkout selects that root. Ordinary
`--mount` options do not change the starting directory; mounting a directory at
`/workspace` puts it at the default starting location. `shell` and `start` reuse
the saved starting directory.
Checkout sharing requires Git on the host; Git validates the selected metadata before startup.
A command is required; a bare invocation prints help. Creation requires a name.

Names contain 1-50 lowercase letters, digits, hyphens, or underscores and start
with a letter or digit. Herdr integration limits names to 32 characters;
oversized names are rejected before guest creation.

```sh
agent-sandbox run --name feature
agent-sandbox run --name codex-work --agent codex --mount-git --mount-codex-auth --mount-skills --herdr
agent-sandbox run --name reviewer --mount-git /path/to/worktree --agent opencode --prompt 'Review this checkout'
agent-sandbox run --name tests --mount-git --exec pnpm test
agent-sandbox run --name worker --agent claude
```

Sandboxes are persistent and foreground by default. Exiting a shell, agent, or
custom command leaves the sandbox running. For an attached interactive session
in Codex, run the foreground command in a PTY (`tty: true`) and yield it as a
background terminal with a short
`yield_time_ms`, such as 1000. The running launcher/workload then stays visible
in Codex's background processes. Retain its session ID to read output or send
input. No `--detach` is needed for this workflow.

For an agent supervised through hc messages, launch directly from its supervising
host hc terminal with `--detach --agent codex --prompt 'TASK'`. Scripts can also
use `--detach` (`-d`) when they need an immediate return. It launches a managed
terminal and returns its ID without attaching.
Detach an attached terminal with
Ctrl+Backslash. Both exit and detach leave other terminals running.

`--agent` selects the initial image and program; on an existing sandbox it selects
only the program. You can run multiple agent sessions in the same sandbox. To use
a different product, install its Linux CLI inside the sandbox first. No image
containing every agent is required. `--prompt` requires an explicit `--agent` and
supplies an initial interactive prompt; it cannot be combined with `--exec`.

Open new sessions, discover their IDs, and reconnect:

```sh
agent-sandbox shell --name codex-work
agent-sandbox shell --name codex-work --agent codex --terminal reviewer
agent-sandbox terminals --name codex-work
agent-sandbox attach --name codex-work --terminal reviewer
agent-sandbox shell --name codex-work --exec pnpm test
```

Use another terminal or another Codex background PTY for concurrent sessions.

A shell or agent session runs under the guest's own hc. `attach` reconnects to an
existing terminal; `shell` creates a new one. Without `--detach`, `--exec` runs a
direct command with its ordinary output, stdin, and exit code; it creates no hc
terminal. It supports pipes and has no hc execution timeout. With `--detach`,
custom commands run in discoverable hc terminals too.

`--exec` consumes every remaining argument literally. Put launcher options
before it, and use an explicit shell for shell syntax:

```sh
agent-sandbox shell --name tests --exec sh -lc 'mise trust && mise install && mise run test'
```

The default guest has four CPUs and 4 GB of memory. At creation, use
`--mount-git [PATH]`, `--cpus 6`, `--memory 8G`, or `--image TAG` as needed.
`--home PATH` selects the host state/skills source; its entire contents are not
mounted. Mounts, image, resources, and Herdr integration are fixed at creation.
Apple builds and guests default to DNS resolver `1.1.1.1`; `--dns IP` or
`CONTAINER_DNS` overrides it without changing host DNS settings.

## Stop, restart, and delete

```sh
agent-sandbox status
agent-sandbox stop --name feature
agent-sandbox start --name feature
agent-sandbox delete --name feature
```

`stop` ends all guest processes and stops the VM, retaining its filesystem.
`start` restarts it and opens a new shell or selected agent; it does not restore
live processes from before the stop. Installed tools and guest-local login files
survive stop/start. `delete` destroys the filesystem. Mounted checkout changes
and opted-in host state survive deletion.

Add `--rm` at creation to remove the sandbox automatically when it stops:

```sh
agent-sandbox run --name temporary --rm --detach
agent-sandbox stop --name temporary
```

The sandbox's idle process owns its lifetime. `--rm` applies when the sandbox
stops, including an explicit `stop`; exiting one of its terminals does not stop
it. `--detach` and `--rm` can be combined. Only launcher-owned guests are managed;
existing guests with older ownership labels remain discoverable and deletable.

## Images

| Image                    | Default workload | Agent CLI added |
| ------------------------ | ---------------- | --------------- |
| `agent-sandbox:base`     | Bash             | None            |
| `agent-sandbox:codex`    | Codex            | Codex           |
| `agent-sandbox:opencode` | OpenCode         | OpenCode        |
| `agent-sandbox:claude`   | Claude Code      | Claude Code     |

Chrome and agent-browser are in the common base, so Codex with browser access
uses the ordinary Codex image. There are no browser/agent combinations to build.
`mise run build` builds all four Dockerfile targets sequentially and reuses the
common base layers. To build just one, use
`agent-sandbox build --profile codex`. The Dockerfile's idle command lets the
launcher manage VM lifetime; the launcher chooses the foreground workload.

The amd64 OpenCode image requires an AVX2-capable CPU. Its pinned installation
uses the standard x64 binary; it does not select the baseline binary for older
CPUs. This does not affect the arm64 images used by Apple silicon sandboxes.
OpenCode's [installer](https://opencode.ai/v2/install) checks AVX2 before selecting
its x64 package; this image has the explicit CPU requirement instead.

Images contain no npm, npx, compilers, make, or development headers. Install
repo-specific dependencies inside the guest with mise or APK. These guest disk
changes survive stop/start and disappear on deletion. No host browser or browser profile is mounted.

## Optional Herdr integration

The guest's hc manages terminals even without host integration. `--herdr` adds a
host hc machine registration and labels its terminals for the Herdr app:

```sh
agent-sandbox run --name feature --agent codex --herdr
```

This creates a new app space without changing the selected space. New terminals
in that sandbox join the same space, each in a new tab. The app need not be open
when the terminal starts. Without `--herdr`, no host hc installation is required.
With it, install host hc matching `IMAGE_HC_VERSION` in `mise.toml`.

The host hc core session and the app's space/tab IDs are separate targets:

```sh
# Discover app space and tab IDs
herdr-app ls

# Choose an existing space/tab belonging to this sandbox
agent-sandbox shell --name feature --herdr-space feature/sp123 --herdr-tab feature/tb456

# Choose a host hc core session (defaults to the caller's session)
agent-sandbox run --name worker --agent codex --hc-session work
```

The host core selector implies `--herdr` and is saved with the sandbox. App
space/tab selectors apply to the new terminal created by `shell`; IDs are
validated against the running app. Herdr scopes spaces to machines, so a guest
terminal can join only a space belonging to that same sandbox. The wrapper
removes the machine prefix before sending guest labels; Herdr adds it itself.
A new sandbox gets its own space. Joining a host or another sandbox's space is
not supported by this transport.

The app must be connected to the selected host core to display its machines.
Specifying a core session does not switch the app's core or current selection.

Use the sandbox and terminal addresses to send instructions to a running agent:

```sh
hc send feature/reviewer 'Run the tests and fix failures'
hc read feature/reviewer
hc attach feature/reviewer
```

For a non-default core session, run hc with the same `HC_SESSION`. Without host
registration, use `container exec feature hc send reviewer 'Run the tests'`.

When launched from an hc terminal with `--herdr` targeting the same host core,
managed guest terminals become its native hc children. They keep running when
that parent exits. With another host core, or from outside hc, they have no host
parent. Inside the guest, `hc get "$HC_TERMINAL_ID" --json` shows its parent;
reply with `hc send <parent> 'Task complete'`. Keep the machine prefix in the
parent address: a bare terminal ID identifies a terminal in the guest.

For host-supervised agent work, launch directly from the supervising hc terminal
with an initial prompt, then exchange tasks and reports through hc:

```sh
agent-sandbox run --name worker --detach --agent codex --mount-git --mount-codex-auth --herdr --prompt 'Inspect the checkout, confirm your hc parent, and report readiness to it before starting the assigned task'
agent-sandbox terminals --name worker
hc send worker/TERMINAL_ID 'Run the agreed focused checks and report the results'
```

Replace `TERMINAL_ID` with the discovered guest terminal ID. `--detach` returns
the launcher while the guest agent remains visible in Herdr. Avoid launching
through an extra host hc terminal: it becomes the guest's parent and changes
which supervisor the guest can reach. Confirm the parent route and initial reply
before expensive work. Later `shell` and `start` commands reuse the saved Herdr
settings; `--herdr` is a creation option.

Start acceptance with a small cold build and focused tests under an explicit
resource budget. A test-name filter alone may still compile the full repository.
Keep downloaded tools and reports outside the checkout to avoid lint discovery,
and save the durable handoff outside the guest before teardown. Host permission
checks remain enabled; narrowly scoped lifecycle approvals can reduce repeated
prompts without granting the host agent unrestricted execution.

Transport uses `hc machine add --via 'container exec -i … sh -c'`. No SSH server,
host socket mount, or host core configuration is shared with the guest. A short
guest-local hc socket avoids Unix socket path limits. `stop` removes host
registration and its Herdr space; `start` restores the registration and opens a
new terminal in its space. `delete` unregisters and removes the sandbox and its
Herdr space.
Stopping it through Apple's CLI bypasses the wrapper's registration cleanup.

## Shared files and authentication

### Authentication limitations

Selecting an agent launches its CLI; it does not transfer your host login.
No host credentials or provider environment variables are forwarded by default.

| Agent       | Host authentication reuse                                                                                                                   | What to do in the guest                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Codex       | `--mount-codex-auth` mounts only `auth.json` read-only into the container. Guest token refresh cannot save credentials; see recovery below. | Use the mounted login with its refresh limitation, or sign in in a sandbox without `--mount-codex-auth`. |
| Claude Code | No agent-specific host state mount or config copy is provided. Authenticated model requests and refresh have not been verified.             | Run `claude auth login` inside the guest.                                                                |
| OpenCode    | No agent-specific host state mount is provided. Authenticated model requests and refresh have not been verified.                            | Run `opencode auth login` inside the guest.                                                              |

CLI version checks, browser checks, and fake-state mount tests do not establish
authenticated access to a provider or subscription. Guest-local logins persist
across stop/start and are lost when the sandbox is deleted.

### Available mounts

| Host content                                             | Access                                   | Opt-in                         |
| -------------------------------------------------------- | ---------------------------------------- | ------------------------------ |
| Selected checkout/worktree and its required Git metadata | Read/write, same paths                   | `--mount-git [PATH]`           |
| `~/.codex/auth.json`                                     | Read-only file mount, same path          | `--mount-codex-auth`           |
| `~/.agents/skills` and direct symlink targets            | Read-only, same paths                    | `--mount-skills`               |
| Selected host directory                                  | Explicit `ro` or `rw`, chosen guest path | `--mount SOURCE:TARGET:ro\|rw` |

Mount helpers are independent of the selected agent. Use `--mount-git [PATH]`
for a checkout and its required Git metadata, `--mount-codex-auth` for the
read-only Codex credential file, and `--mount-skills` for read-only shared skills.
Use repeatable `--mount SOURCE:TARGET:ro|rw` for ordinary directories:

```sh
agent-sandbox run --name ac-feature --agent codex --mount-git --mount-codex-auth --mount-skills \
  --mount "$HOME/Documents/reference:/reference:ro" \
  --mount "$HOME/Documents/sandbox-output:/output:rw"
```

No checkout, worktree, Git metadata, agent state, or shared skills are mounted
by default. Codex requires a regular `auth.json` file under the selected `--home`;
shared skills require the corresponding skills directory. Each mount is printed
before creation, including host source, guest target and access mode. Directory
sources must already exist; quote paths containing spaces. Targets must be
absolute guest paths and the access mode is required. Relative source paths are
resolved from the caller's working directory; symlinks resolve to their canonical
host directory. Nested symlinks do not add shares.

`--mount-git [PATH]` selects one working checkout and its starting directory.
Additional directory mounts do
not discover or share external Git metadata; use self-contained checkouts when
mounting additional repositories. Generic directory targets cannot overlap other
mounts,
the selected checkout, or reserved runtime paths. The guest home itself and host
home directory cannot be mounted wholesale. With `--mount-codex-auth`, generic
mounts cannot expose other state from the selected host Codex directory or cover
its guest directory.
Writable aliases of shared skills are rejected. Mount settings are fixed at
creation; `shell` and `start` reuse them.

Claude and OpenCode use guest-local authentication, configuration and history by
default. Their agent-specific host state-mount presets are unsupported. Generic
directory mounts share the paths you explicitly select; sharing authentication
directories this way does not establish a supported provider-login workflow.

Mounts are printed before startup. The selected checkout and opted-in shared Git refs
can be modified or deleted by the agent. Sibling working-tree paths are not
mounted, but repository history and committed files on other branches remain accessible.
Host SSH/AWS directories, credential helpers, signing agents, global
Git configuration, runtime control sockets, and host hc state are not
automatically mounted. Generic directory shares grant access to the selected paths.
Configure a guest Git identity if it needs to commit. `gh` is installed without
mounting host GitHub credentials; authenticate inside the guest if needed. Image builds never include
checkout contents, user configuration, or credentials.

Credential exclusion is not an enforced push-approval mechanism. The guest has
network access and can publish if it obtains credentials. When publication needs
manual approval, keep it on the host and do not provision publishing credentials
in the guest; this remains an operating policy rather than a technical block.

With `--mount-git [PATH]`, Git metadata inside the selected checkout stays visible.
For linked worktrees, the validated common Git store is shared automatically
so status, staging, and commits work. A path inside a checkout selects its root.
Ordinary checkouts and registered linked worktrees are supported; symlinked
`.git` paths, separate Git directories, and submodule gitfiles are not.
This does not share host Git configuration or credentials. No additional
metadata stores are discovered through `.jj` links.

### Codex read-only authentication

With `--mount-codex-auth`, the launcher passes only the existing host
`~/.codex/auth.json` to Apple Container through `--volume`, read-only at the same
path inside the guest. The host file stays in place. It must be a regular file,
not a symlink. The rest of the guest `.codex` directory stays writable and local;
the auth helper does not mount host configuration, hooks, history, sessions or
databases into the container process. Other opt-in mounts grant access to their
selected paths. Shared skills require `--mount-skills`.

**Runtime boundary:** Apple Container 1.7.1 implements a single-file mount by
sharing its parent directory with the underlying VM and bind-mounting the file
into the workload. The ordinary container process sees only the selected file;
the VM itself has access to the parent directory. This is not an auth-only export
at the VM boundary. See Apple's
[single-file mount trade-offs](https://github.com/apple/containerization/blob/0.54.0/docs/single-file-mounts.md#trade-offs).

**Refresh limitation:** the guest can read the login but cannot save refreshed
credentials, replace the mounted file, or complete a login that writes to it.
Codex saves credentials using a temporary sibling file and an atomic rename;
a writable single-file mount would also reject that replacement. A host-side
atomic replacement can leave a running mount stale or unreadable. Do not assume
that host login changes appear in a running sandbox, or that a successful initial
request proves future refresh will work.

Read-only access protects the host file, not the login at the provider. Guest
refresh or logout can affect the shared grant before a local credential write
fails; the host may also need a fresh login afterward.

If Codex reports a read-only credential file, `EBUSY`, a missing `auth.json`, or an
authentication/refresh failure:

1. Keep the sandbox and its work. If the host login needs renewal, sign in on the
   host using file-backed storage:

   ```sh
   codex -c 'cli_auth_credentials_store="file"' login
   ```

2. Check whether the sandbox was created with `--rm` before stopping it. For
   `--rm`, first export guest-local work and save a verified handoff outside the
   sandbox. Stopping deletes its guest filesystem; recreate it with the renewed
   host auth file instead of using `start`.

   For a persistent sandbox created without `--rm`, stop and start it to attach
   the current host auth file again:

   ```sh
   agent-sandbox stop --name codex-work
   agent-sandbox start --name codex-work --agent codex
   ```

3. If the problem continues, create a sandbox without `--mount-codex-auth` and use
   `codex login --device-auth` inside it. That guest has writable, independent
   credentials. Keep or export the old sandbox's work before deleting it.

Managed Codex starts with
`--no-daemon --dangerously-bypass-approvals-and-sandbox` and
`cli_auth_credentials_store="file"`. Keychain-only host login is not transferred.
Guest-local credentials persist across stop/start and are lost on deletion.

Managed Codex launches keep SQLite databases in the guest at
`/var/lib/agent-sandbox/codex` using `sqlite_home`. They persist across stop/start
and disappear on deletion. These databases include goals and memory-processing
state, as well as conversation indexes. Shared transcript files cannot restore
all database state. Only authentication is deliberately shared with the host;
configuration, transcripts, and generated memories stay in the guest and are
lost on deletion unless exported. Host and guest conversation lists and memory
processing are separate.

Several host Codex processes share one kernel's file locks and memory mappings.
Apple containers use separate Linux kernels and expose host directories through
VirtioFS. File access alone does not establish correct cross-kernel coordination
for SQLite WAL and its shared-memory index. We previously encountered a database
backfill timeout with shared host SQLite. We keep databases guest-local because
concurrent host/guest use is unverified. This is a deliberate limitation, not a
claim that SQLite cannot support multiple processes. Codex documents cross-host
sharing over Linux NFS with rollback journals and verified file locks. That
procedure does not establish support for Apple's VirtioFS mounts. See
[SQLite WAL requirements](https://www.sqlite.org/wal.html),
[Codex shared-home guidance](https://learn.chatgpt.com/docs/environments/network-file-systems),
and [Apple mount types](https://github.com/apple/container/blob/main/docs/volumes.md).

The container also sets `CODEX_SQLITE_HOME` for custom launches;
an explicit `sqlite_home` in your configuration takes precedence over that
environment variable. Managed launches disable startup update checks so the
pinned image version starts without an update dialog.

### Worker handoff

Treat sandbox agents as replaceable workers. The host orchestrator owns durable
outcomes and decisions. Sandboxes remain persistent and foreground by default;
this workflow does not change their lifecycle defaults.

Include the return address and final-report requirements in the worker's initial
prompt. Use hc's parent route when available, or collect the foreground output.
Require results, decisions and reasons, changed files and commit IDs, test
commands and results, and unfinished work.

Before `delete`, or before stopping a sandbox created with `--rm`:

1. Verify receipt of the final report. Retain the sandbox if the report is incomplete.
2. Verify the reported changes, commit IDs, and tests from the host.
3. Save the verified report outside the sandbox. Record lasting decisions in project documentation or a durable task handoff.
4. Verify that work exists in the shared checkout or an export outside the sandbox.

Guest SQLite is expendable only after this handoff. A chat reply alone does not
replace the durable record. The wrapper does not copy or merge databases,
generate host Codex memories, or enforce this handoff in `delete`. The orchestrator
must complete it. Transcript and memory files are guest-local even with the
Codex auth mount and disappear on deletion unless exported.

### Other agent state

Claude and OpenCode use guest-local state by default. Sign in inside the guest;
the launcher provides no agent-specific host authentication mount or Claude
configuration copy. A persistent guest keeps its local state until deletion;
an automatically removed guest loses it when the sandbox stops. Claude retains
its normal permission prompts. Codex skill links into `~/.agents/skills` need
`--mount-skills` too.

Shared skills can reference macOS tools, MCP servers, or host-only paths. Those
require Linux equivalents; host Codex configuration is not loaded. The guest cannot update the mounted host login cache.
Host skills are unavailable unless explicitly exposed through `--mount-skills`. Shared skills are read-only files; discovery rules vary by agent.

`.codex` itself must be a real directory. Skill links must point directly to
canonical targets; chained links are rejected. Direct links in the host skills
directory approve additional skill roots. Nested links must stay inside those
roots and never add host mounts. Skills directories with symlinked ancestors
are rejected. Codex credential-file symlinks and overlapping checkout/auth mounts
are rejected. Mounts that expose the whole host home are rejected.

## Repository mise configuration

The mounted checkout contains its mise configuration. Review it, then run
`mise trust`, `mise install`, and its tasks inside the guest. System dependencies
can be declared with `[bootstrap.packages]` and applied with
`mise bootstrap packages apply --manager apk`. See the tested examples and
compatibility limits in [the Wolfi choice](docs/base-image.md).

The image does not automatically trust repo configs or run their hooks. Mise
selects language tools; Wolfi APK supplies native libraries, compilers, and
headers as needed. Wolfi uses glibc, but Debian package names, `apt` commands,
and every prebuilt binary are not universally compatible. Do not mix Alpine
and Wolfi packages. Guest tool caches survive stop/start and disappear on deletion, except for
files within explicitly mounted host state.

## Checks and CI

```sh
mise tasks
mise run fmt
mise run check
mise run audit
mise run build
mise run check:image
mise run scan
mise run smoke:cli
```

`check` runs format/lint checks, TypeScript, unit tests, lock validation, and
Chrome stable-version freshness (requires network access).
Biome covers JavaScript/TypeScript, Markdown, JSON, and YAML throughout the repo.
Shell scripts use shfmt and ShellCheck because Biome does not support shell.
Both shell checks run through `lint` and `check`; `fmt` also formats shell scripts.
`check:image` tests all four image inventories, agent separation, and an actual
agent-browser page load. `smoke:cli` uses fake state and a disposable linked
worktree to test shell/custom commands, literal arguments, exit status, state
persistence, mount boundaries, optional hc integration, and teardown. Its hc
server uses scratch configuration/state and a separate session. It makes no
model request and does not change the selected session in your normal core.

With Herdr already open, `mise run smoke:herdr` creates a separate test sandbox,
opens two terminals in its existing app space/tab, checks that the selected
session stays unchanged, and deletes the test sandbox. It uses no agent login.

Run `mise run smoke:codex` for the full live Codex lifecycle. It requires an
existing file-backed ChatGPT login, installed agent skills, open Herdr, host Git, hc, and
the host `privacy-gate` command. It mounts your normal `auth.json` read-only and shared
`.agents/skills`, verifies login and skill access, and sends an initial task to
Codex in a throwaway linked worktree. The test independently checks the result,
runs the host privacy gate, commits through the guest and asks Codex to verify
and report the commit, opens another shell, runs an exec
command, checks stop/start persistence, and deletes the sandbox.

Codex sends progress and commit reports directly to its host hc parent using
hc's native return connection. The test verifies that parent relationship and
receipt of the reports. It uses your default host hc core, verifies the sandbox
appears in Herdr, and cleans up only its own machine and orchestrator terminal.
Before teardown, it receives a structured final handoff, verifies its content,
and saves `handoff.json` outside the sandbox. It verifies that the handoff and
commit survive deletion. If the test fails before recording the handoff, it
stops and retains its sandbox for recovery.
It retains its fixture,
commit, and `report.json` under `.artifacts/codex-lifecycle-*`. It makes real
model requests using your subscription and is excluded from CI.

CI builds all profiles on amd64 and arm64, checks each, and runs Trivy image
scans. `build:ci`, `check:image:ci`, and `scan:ci` use Docker on Linux. Repository
Trivy and pnpm audits of the root and four image-profile graphs are separate audits; Chrome
freshness also runs in the required local `check`. CI runs daily at **00:00 UTC**, plus push, pull request, and manual
triggers. The workflow becomes active when commits are pushed to the GitHub remote. There are no dependency update PR bots.

Unsuppressed HIGH/CRITICAL findings fail the security gates, including unfixed
findings. The explicit picomatch exception expires on 2026-12-18; see
[reproducibility](docs/reproducibility.md#vulnerability-checks).
Complete Trivy reports remain under `.artifacts/` and in CI artifacts. Scanner
coverage of downloaded native binaries and Chrome is limited; version/checksum
and browser freshness checks complement the scans. See [verification](docs/verification.md)
for tested behavior and limits.
